# 제안 검토: "저장 여부를 물어보고, 저장한 책만 중복 제외"로 바꾸면 폴백목록 소진 문제가 없어지는가

## 결론부터

**아니요, 없어지지 않습니다.** 이 변경은 폴백 풀이 소진되는 *속도를 늦출 수는*
있지만, `recommend-debug-notes.md`에 정리된 근본 원인(폴백 목록이 별자리/MBTI와
무관하게 항상 고정된 10권뿐이라는 것)은 그대로 남아있기 때문에, 저장을 반복하는
사용자는 결국 다시 같은 문제를 겪습니다.

## 1. 현재 코드가 실제로 하는 일 (`functions/api/recommend.js`)

- 로그인 사용자는 매 요청마다 `fetchPreviouslyRecommendedTitles`로 이전 추천
  이력 전체를 가져와 `excludeTitles`로 사용하고, 추천이 끝나면
  `saveRecommendedBooks`로 **자동으로, 물어보지 않고** 이번 추천 결과를 저장합니다.
- `selectBooks`는 LLM 추천 + 폴백 후보 모두에서 `excludeTitles`에 있는 제목을
  제거합니다. 폴백 목록(`buildFallbackBooks`)은 항상 동일한 10권
  (아몬드, 채식주의자, 불편한 편의점, 데미안, 어린 왕자, 나는 나로 살기로 했다,
  언어의 온도, 코스모스, 미움받을 용기, 사피엔스)입니다.
- 즉 지금도 "중복 안 되게 하는" 로직은 이미 있습니다. 사용자가 제안한 기능
  ("다시 추천받을 때 저장한 도서와 중복 안 되게")은 **이미 구현되어 있는 동작**이고,
  바뀌는 부분은 "자동 저장 → 사용자에게 물어본 뒤 저장"뿐입니다.

## 2. 제안대로 바꾸면 실제로 달라지는 것

- 저장을 **거부**한 추천 결과는 이력에 안 쌓이므로, 다음 번 추천 때 그 책들이
  다시 나올 수 있습니다 (중복 방지가 "사용자가 저장을 선택한 책"으로 범위가
  좁아짐).
- 그 결과 `excludeTitles` 집합이 지금보다 천천히, 사용자가 실제로 저장을
  선택한 만큼만 커집니다. → 폴백 풀이 소진되기까지 걸리는 시간/요청 횟수가
  늘어나는 것은 맞습니다.

## 3. 그런데도 왜 "해결"은 아닌가

- 폴백 풀 자체는 여전히 **고정 10권**입니다. 저장을 계속 선택하는 사용자
  (오히려 서비스를 제일 좋아하는, 저장 기능을 제일 잘 쓰는 사용자)는 결국
  10권을 다 소진하고, 11번째부터는 다시 "폴백 후보가 부족해서 10권을 못 채우는"
  원래 문제로 돌아갑니다. 즉 문제를 없애는 게 아니라 **지연**시킬 뿐입니다.
- 오히려 부작용도 있습니다: 저장을 거부한 책이 다음 요청에도 다시 추천될 수
  있으므로, "매번 새로운 책을 추천받고 싶다"는 사용자 입장에서는 체감 다양성이
  떨어질 수 있습니다.
- LLM이 추천하는 책은 사실상 무한한 후보 풀이라 소진 문제가 없습니다. 소진은
  전적으로 "OpenAI 키가 없거나 LLM 추천이 부족할 때 채우는 고정 폴백 10권"
  구조에서만 발생합니다. 저장 트리거를 자동/수동 중 무엇으로 하든 이 구조는
  그대로입니다.

## 4. 실제로 소진 문제를 없애려면 (디버깅 노트의 "다음 단계 (A)"와 동일한 방향)

- `buildFallbackBooks`가 반환하는 목록을 10권 고정이 아니라 20~30권 이상으로
  늘리고, 가능하면 별자리/MBTI 조합별로 다양화한다.
- 폴백 풀도 소진될 수 있으므로, 이력에 있는 책이 폴백 후보 전체보다 많아지면
  (예: 남은 후보가 0이 되면) 오래된 이력부터 제외 대상에서 풀어주는 등
  "완전히 못 채우는" 상황 자체를 막는 보완 로직이 필요하다.
- 유료 플랜 전환(subrequest 한도 상향)은 "순서상 뒤에 있어 검증을 못 받고
  탈락하는" 문제(디버깅 노트 5번의 1번 항목)는 해결하지만, 폴백 풀 고정
  문제와는 무관하다.

## 5. 저장 여부를 물어보는 기능 자체에 대해

- UX 관점에서는 유효한 기능(사용자가 원치 않는 책까지 "본 이력"으로 남기고
  싶지 않을 수 있음)이라 구현할 가치는 있습니다.
- 다만 이번 질문의 목적("폴백 소진 문제 해결")과는 별개의 기능으로 봐야 하며,
  이 기능만으로 폴백 소진 문제를 없앨 수 있다고 기대하면 안 됩니다.
- 구현하려면: 프론트엔드(`src/App.jsx`)에 추천 결과 표시 후 "저장하시겠어요?"
  확인 UI 추가, 백엔드는 `saveRecommendedBooks`를 추천 시점에 자동 호출하는
  대신 별도의 저장 API로 분리(예: `POST /api/recommend/save`)해서 사용자가
  확인을 누른 뒤에만 호출하도록 변경.

# 폴백이 왜 필요한가

`selectBooks`(`functions/api/recommend.js`)가 매 요청마다 항상 "10권"을
채우려고 하는데, LLM(OpenAI) 추천만으로는 10권이 항상 채워진다는 보장이
없기 때문입니다. 폴백은 그 부족분을 메우는 안전망입니다. 구체적으로 4가지
경로에서 부족이 생깁니다.

## 1. OpenAI API 키 자체가 없을 때 (완전 대체)

```js
if (!env.OPENAI_API_KEY) {
  const fallbackBooks = await selectBooks([], zodiac, mbti, env, excludeTitles)
  ...
}
```
- 이 경우 LLM 호출 자체를 안 하고 `selectBooks([], ...)`로 빈 배열을 넘기므로
  결과 10권 전부가 폴백에서 나옵니다. (로컬 개발 환경에 키를 안 넣었거나,
  키가 만료/삭제된 경우 서비스가 완전히 죽는 대신 그래도 뭔가는 보여주기
  위한 장치.)

## 2. LLM이 정확히 10권을 안 주거나 중복 제목을 줄 때

- 프롬프트로 "10권, 서로 다른 장르로"라고 요청은 하지만, LLM 출력은
  강제되지 않습니다. 실제로 9권만 주거나, 같은 책을 두 번 주는 경우가
  있습니다. `dedupByTitle`이 중복 제목을 제거하면 10권 밑으로 떨어질 수
  있습니다.

## 3. `resolveVerifiedBooks`의 "실존 검증" 필터에서 걸러질 때

```js
// LLM이 지어낸 책이거나 미번역 원서일 수 있어, 알라딘/예스24/교보문고 중
// 한 곳에서라도 검색되지 않으면 채택하지 않는다.
```
- LLM은 가끔 실제로 존재하지 않는 책(할루시네이션)이나, 한국에 정식
  번역 출간되지 않은 원서를 추천합니다. 이런 책은 국내 서점 3곳
  어디서도 표지 검색이 안 되므로 `resolveVerifiedBooks`가 걸러냅니다.
  → 검증을 통과 못 한 만큼 10권에서 빠집니다.
- Cloudflare subrequest 예산이 부족해 표지 검색 자체를 못 하고 넘어간
  책도 "검증 실패"로 취급되어 같이 걸러집니다(`recommend-debug-notes.md`
  참고).

## 4. `excludeTitles`(로그인 사용자의 이전 추천 이력)로 제외될 때

- 이번 대화 앞부분에서 다룬 부분입니다. LLM이 프롬프트의 "겹치지 않게"
  지시를 무시하고 이전에 이미 추천한 책을 다시 줄 수 있는데, 이 경우도
  `selectBooks`에서 제외되어 10권에서 빠집니다.

## 요약

폴백이 없다면: 위 네 가지 경우 중 하나라도 발생하면(실제로는 매우 자주
발생) 사용자에게 10권이 아니라 6권, 4권, 심하면 0권짜리 추천 화면을
보여주게 됩니다. 폴백은 "LLM 경로가 부족한 만큼만" 고정된 후보 목록에서
채워 넣어, 사용자 경험상 항상 10권에 가깝게 채워주는 최종 안전망 역할을
합니다. (다만 이 폴백 목록이 고정 10권이라는 점이 바로 이전에 다룬
"폴백 소진" 문제의 원인입니다.)

# 제안 검토: "LLM에게 10권 한 번에 요청하지 말고, 1권씩 요청 → 중복이면 재요청"

## 결론부터

**권장하지 않습니다.** 이 방식은 하필 지금까지 커밋 5개(`0d5c2fb`~`ea814ad`)를
들여 고친 문제(subrequest 한도 초과로 이력 저장이 실패하던 버그)를 다시
악화시킵니다. 폴백 소진 문제와도 직접 관련이 없습니다.

## 왜 subrequest 예산을 더 심하게 갉아먹는가

`functions/api/_fetchBudget.js`는 `globalThis.fetch`를 통째로 감싸서 **OpenAI
호출이든 표지 검색이든 구분 없이** 모든 fetch를 하나의 카운터로 셉니다.
현재 예산은 `BUDGET = 20, RESERVED = 5` (즉 이력 저장용으로 5개를 남겨두고
15개까지만 자유롭게 씀), 그 15개 안에서:

- 지금: OpenAI 호출 **1회** + 표지 검색 (책 1권당 최대 6회, 다만 예산 소진되면
  중간에 스킵됨)
- 제안대로 바꾸면: 책 10권을 다 채우기까지 OpenAI 호출이 **10회 이상**
  (LLM이 중복/할루시네이션 책을 주면 재요청까지 더해져 실제로는 10회보다
  많아질 가능성이 큼) + 여전히 책마다 표지 검색 최대 6회.

즉 지금도 빠듯한 15개의 여유 예산을 표지 검색과 나눠 쓰던 것을, OpenAI 호출
자체가 10개 이상을 잡아먹게 되어 **표지 검색은 몇 권 하기도 전에 예산이
바닥나고**, `saveRecommendedBooks`(이력 저장)까지 다시 실패할 위험이
커집니다. 지금까지 고친 버그가 그대로 재발하는 구조입니다.

## 다른 부작용

- **속도**: OpenAI API 호출 1번은 보통 1~3초 걸립니다. 10번을 순차로(혹은
  중복 시 재요청까지) 호출하면 사용자가 추천 버튼을 누르고 10초~수십 초를
  기다려야 할 수 있습니다. 지금은 호출이 1번뿐이라 훨씬 빠릅니다.
- **비용**: 호출마다 시스템/사용자 프롬프트(별자리, MBTI, 제외 목록, 조건
  설명 등)를 매번 다시 보내야 하므로, 실제 생성되는 토큰(책 1권 분량)에
  비해 반복되는 고정 비용(프롬프트 토큰)이 10배로 늘어납니다.
- **무한 재요청 위험**: LLM이 같은 별자리/MBTI 조합에 대해 비슷한 답을
  반복하는 경향이 있어(특히 온도를 낮추면 더), 중복이면 재요청하는 루프가
  종료 조건 없이 여러 번 반복될 수 있습니다. 상한을 두더라도 그만큼 fetch를
  더 씁니다.

## 폴백 소진 문제와의 관계

이 변경은 "LLM이 이전 추천작과 중복되는 책을 주는 것"을 더 확실히
막으려는 시도로는 이해가 됩니다만, 지금도 프롬프트에 제외 목록을 넣고
(`excludeNote`) `selectBooks`에서 다시 한번 `excludeTitles`로 걸러내므로
중복 방지 자체는 이미 이중으로 되어 있습니다. 폴백이 소진되는 진짜 원인은
"LLM이 중복을 준다"가 아니라 "폴백 목록이 고정 10권"이라는 점이므로, 이
변경으로는 폴백 소진 문제가 해결되지 않습니다.

## 중복을 더 확실히 막고 싶다면 (예산을 늘리지 않는 대안)

- 지금처럼 10권을 한 번에 요청하되, 응답에서 걸러진 뒤 여전히 부족하면
  **부족한 개수만큼만** 짧게 한 번 더 요청(예: "3권만 더 추천해줘, 이미
  준 목록과 아래 제외 목록과도 겹치지 않게")하는 정도가 절충안입니다.
  이러면 최악의 경우에도 OpenAI 호출이 2회로 끝나 예산 부담이 크게 늘지
  않습니다.

# 결정: "폴백 30개로 늘리고 중복체크 제거" 대신 "제외 범위를 최근 이력으로 축소"

## 전제 확인

- OpenAI 키가 없는 상황(완전 폴백 모드)은 실제로 발생하지 않는다고 확인함.
  → 폴백은 "LLM 후보가 검증 실패/중복으로 부족할 때 몇 권만 채우는" 용도로만
    쓰이고, 10권 전부가 폴백에서 나오는 경우는 사실상 없다는 뜻. 그만큼
    폴백 풀 고갈의 실제 심각도는 처음 가정보다 낮음.

## 기각한 안: 중복체크 제거 + 폴백 30개

- 중복체크(`excludeTitles`)를 아예 없애면 폴백 소진 자체는 사라지지만,
  이 프로젝트가 원래 원했던 "다시 추천받을 때 중복 방지" 기능 자체가
  없어짐(요구사항과 정면 배치).
- 게다가 `buildFallbackBooks`는 고정 순서 배열이고 셔플 로직이 코드 어디에도
  없어서(`Math.random`은 배경 애니메이션에만 쓰임), 제외 로직이 없으면
  항상 배열 앞쪽 10개만 뽑히고 11~30번째 항목은 절대 노출되지 않음.
  → 30개로 늘려도 사실상 죽은 코드가 되어 효과가 없음.

## 채택한 안: `fetchPreviouslyRecommendedTitles`의 제외 범위를 "전체 이력"에서
  "최근 N건"으로 축소

- 현재(`functions/api/recommend.js`)는 `recommended_books`에서 해당
  `user_id`의 **모든** 행을 가져와 제외 대상으로 삼음 → 이용 횟수가 쌓일수록
  제외 집합이 무한히 커져 결국 폴백 풀(고정 10권)을 다 써버림.
- `recommended_books` 테이블에 이미 `created_at`(timestamptz, `now()` 기본값)
  컬럼이 있으므로(`supabase_recommended_books.sql`), 쿼리에
  `order=created_at.desc&limit=N`을 추가해 최근 N건만 가져오도록 바꾸면 됨.
- 효과: 최근에 본 책과는 안 겹치게 하면서도, 그보다 오래전에 추천했던 책은
  시간이 지나면 다시 후보 풀로 복귀함 → "영구 고갈"이 구조적으로 불가능해짐.
  중복 방지 기능(원래 요구사항)은 그대로 유지됨.

## 남은 결정 사항 (다음에 구현할 때 정할 것)

- N 값: 폴백 풀 크기(현재 10권)보다 작게 잡아야 함. N을 풀 크기와 같거나
  크게 잡으면, 한 번 풀 전체가 최근 이력에 다 들어가는 순간 다시 0권으로
  돌아가는 예전 문제가 재현될 수 있음. 예: N=5 정도면 항상 최소 5권은
  폴백에서 뽑을 수 있음이 보장됨.
- 폴백 풀을 20~30권으로 늘리고 별자리/MBTI별로 다양화하는 것은 이번
  결정과 별개로 여전히 유효한 개선 방향(이번엔 셔플/로테이션 로직도 같이
  넣어야 늘린 만큼 실제로 활용됨). 우선순위는 낮음 — OpenAI 키가 항상
  있다는 전제 하에 폴백 사용 빈도 자체가 낮으므로.
- 구현 시점: 이번 대화에서는 코드 변경 없이 결정 사항만 기록. 실제 구현은
  다음에 별도로 요청.
